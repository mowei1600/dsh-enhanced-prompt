## 1. 产品识别

### 1.1 「增强提示词」属于哪个 WorkBuddy

**同名的确有多个产品，必须先排除：**

- `workbuddy.com` 是美国的**外勤/工单管理 SaaS**（Job Management、Scheduling and Dispatch、Field App 等模块）[S21]。该站无任何 AI 提示词相关功能，与本课题无关。
- 中文语境下「增强提示词 / 提示词增强」指向的是**腾讯的 WorkBuddy**。

**【已核实】产品身份**

| 项目 | 内容 | 来源 |
| --- | --- | --- |
| 厂商 | 腾讯（腾讯云），协议主体「腾讯云计算（北京）有限责任公司」 | [S1][S11] |
| 定位 | 「全场景 AI 办公工作台」，自然语言下达任务，自主规划执行，交付文档/表格/PPT | [S1][S2] |
| 中国站官网 | `https://www.workbuddy.cn/` | [S3] |
| 国际站 | `https://www.workbuddy.ai/`（"AI Agent for Everyday Office Work"） | [S13] |
| 腾讯云产品页 | `https://cloud.tencent.com/product/workbuddy` | [S1] |
| 客户端形态 | 桌面客户端（Windows / macOS）为主，另有小程序端、移动端、企业版 | [S1][S5] |
| 版本号（调研时最新） | **5.11.3（2026-11-15）**；更新日志可回溯至 4.22.x | [S4] |
| 姊妹产品 | CodeBuddy（账号体系、积分与 WorkBuddy 互通） | [S11] 8.1.3、8.4.5 |

> 注：`goworkbuddy.cn`、`workbuddy-dl.com`、`workbuddy-chat.net` 等域名均为**第三方教程站/下载站**，不是官方渠道，其内容不作为事实依据（仅作交叉参考）。[S22]

### 1.2 入口位置

**【已核实】**「增强提示词」是**输入框（composer）旁的一个按钮**，与「语音输入」按钮并列：

> 「除了【项目】模块，输入框旁边多了两个不起眼的小按钮——【增强提示词】 和 【语音输入】。」[S14]（同一文本亦被转载于 [S15]）

**【已核实】** 该按钮**默认不显示**，需先在输入框里输入文字后才出现——这正是大量用户反馈“找不到该功能”的原因：

> 「很多小伙伴找不到这个功能……主要原因是你要先输入你的提示词，输入之后增强提示词功能才会显示出来。」[S16]

**【已核实】** 官方更新日志中**从未出现「新增增强提示词」这类上线公告**，该功能只以“缺陷修复”条目出现 [S4]。与「没有公告，没有推送，就这么悄悄在那」[S14] 的描述一致。

> **【推断】该功能是静默上线（灰度/无公告），而非正式发布的主推能力。**
> 依据：①官方 Changelog 全量扫描无“新增”条目 [S4]；②官方操作手册完全未收录该功能（见 1.3）[S5][S6][S7]；③作者明确观察到“没有公告、没有推送” [S14]。置信度：高。

### 1.3 官方文档的“缺席”证据（关键负向发现）

**【已核实】** 我逐节核对了一份专门讲“任务输入与引导”的官方文档，它把输入框的**每一种**输入方式都写全了，唯独没有「增强提示词」：

该页小节依次为：预览提示词模板、语音输入、音频转文字、拖拽添加文件、超长粘贴自动收起、召回历史输入、添加微信聊天记录、斜杠命令（Slash Command）补全、@ 浏览器操作 [S5]。「创建任务」「任务对话」两页同样没有该功能 [S6][S7]。

> **【推断】「增强提示词」当前属于未写入官方手册的“隐藏功能”，官方未承诺其行为契约。**
> 依据：上述文档对输入框能力的覆盖是穷举式的（连“超过 3000 字符自动收起”“最多 50 个文件”这种细节都写了）[S5]，却完全遗漏该按钮。置信度：高。
>
> **对复刻的直接含义**：不存在可依赖的官方规格说明书；任何“WorkBuddy 增强提示词如何工作”的精确断言，都应默认视为未证实。

## 2. 输入处理

### 2.1 输入框本身能采集什么（官方已核实）

以下为 WorkBuddy 输入框**整体**的输入能力，来自官方文档 [S5][S6]：

| 输入方式 | 官方描述要点 |
| --- | --- |
| 直接文本 | 核心方式，“用一句话描述需求” |
| 语音输入 | Mac `⌥` / Windows `ALT`；录音时输入框实时显示识别文字；**“录音结束后，模型会对识别出的文字进行调整，并将处理后的内容填入输入框”**；结束后输入框保持聚焦可继续编辑 |
| `@` 引用 | 引用文件、文档、规则等上下文 |
| 粘贴图片 | `Ctrl/Cmd + V` 直接粘贴剪贴板图片 |
| 上传 / 拖拽 | 拖拽到页面任意位置即可；最多 50 个文件；单文件大小不限；添加后**不自动发送** |
| 超长粘贴 | **超过 3000 字符**自动收起为可展开条目；悬停预览原文；点击展开可继续编辑 |
| 历史召回 | 输入框为空时按 `↑` 逐条回溯**最近 20 条**已发送内容；`↓` 反向；调出后可改再发 |
| 转发聊天记录 | 微信/企微“转发到其他应用”→ 腾讯 WorkBuddy；最多 **3 段**；卡片形式 |
| 斜杠命令 | 输入 `/` 触发项目级命令补全 |
| 音频转文字 | 支持 wav/mp3/m4a 等；单文件 ≤1GB，时长 ≤5 小时；按约 0.6 积分/分钟计费 |

> **【推断】「增强提示词」消费的是“输入框当前文本”这一层，而不是完整的上下文栈。**
> 依据：①按钮必须“先输入提示词”才出现 [S16]，说明其触发条件绑定的是文本框内容；②官方 bug 记录用“**回流**”一词（见 2.2），说明结果是写回输入框的文本，而不是重新组装上下文。置信度：中。
>
> **【未知】** 增强时是否把 `@` 引用、附件、历史对话一并纳入改写上下文——所有来源均未提及。
>
> 对复刻的含义：**保守做法是先只增强文本框文本**，把附件/引用作为“不参与改写、原样保留”的对象，避免语义被错误吸收。

### 2.2 与输入框联动的官方旁证

**【已核实】** 官方 Changelog 有两条直接关于该功能状态管理的缺陷修复 [S4]：

- `5.1.0`（2026-06-13）：「修复**增强提示词跨会话泄漏**问题」
- `5.3.7`（2026-07-29）：「修复**增强提示词回流误判**的问题」

> **【推断】两点工程含义。**
> ①“回流”＝改写结果被写回输入框（write-back），与 2.1 的用户观察一致；
> ②“跨会话泄漏”说明该功能的改写结果/状态曾是**跨会话共享**的全局状态，属于典型实现缺陷——复刻时应把增强结果严格**绑定到单个会话/单条草稿**。置信度：高（用词本身即证据）。

### 2.3 长度、语言

- **【已核实】** 输入框层面的已知阈值：超长粘贴 3000 字符触发收起 [S5]；附件 ≤50 个 [S5]；音频 ≤1GB / ≤5 小时 [S5]。
- **【未知】** 增强器自身的输入/输出长度上限，无任何来源。
- **【已核实】** 界面以中文为主，且存在海外版/多语界面（巴西葡萄牙语、印尼语）[S4]；海外版亦曾出现「提示词增强不可用」缺陷 [S4]。
- **【推断】** 增强器应至少支持中英双语输入（因为海外版存在该功能 [S4]），但**是否保持输入语言输出**无证据。置信度：低-中。

## 3. 提示词改写策略

> **前提声明**：官方对改写策略**零披露**——没有系统提示词、没有模型名、没有温度、没有候选数、没有 schema。本节区分“可观察到的效果描述”与“不可见的实现”。

### 3.1 可观察到的改写效果（二手，但多源一致）

**【已核实】** 三个独立来源对“增强后变成什么”的描述高度一致：

| 来源 | 原文 |
| --- | --- |
| [S14] / [S15] | 「它帮你**补齐角色设定、背景信息、任务拆解、输出格式**，一套完整的提示词自动生成。」 |
| [S16] | 「把你写的不是很明确的提示词**自动补全成一条结构完整、可直接执行的指令**。具体就是**补全关键信息、提升结果准确度、降低使用门槛**」 |
| [S17] | 「你输入一句话的模糊需求，WorkBuddy 自动帮你**展开成一段结构化、精准的指令**」「就像在你和 AI 之间加了一个翻译」 |

> **【推断】改写目标是把“一句话模糊意图”升格为“可执行的需求规格”。**
> 依据：三源一致的四要素（角色 / 背景 / 任务拆解 / 输出格式）+ “可执行”措辞。置信度：高。
>
> 注意：**“角色设定、背景信息、任务拆解、输出格式”是对效果的概括，不是官方 schema**，不要当成字段清单直接照搬。

### 3.2 「六段式」的正确位置（纠正一个易混淆点）

伙伴站 `workbuddy.press`（页脚自述“WorkBuddy/CodeBuddy 官方授权合作伙伴 · 易尚云”）的「提示词库」给出一个六段式写法 [S18]：

```
目标：我要完成什么工作，给谁使用。
输入：要读取哪些文件、目录、网页或数据，时间范围是什么。
动作：先检查什么，再分析什么，最后生成什么。
约束：哪些内容不能猜，哪些文件不能修改，哪些动作必须先确认。
输出：文件名、格式、章节、字段和保存位置。
验收：用行数、合计、引用位置、页面数量或抽样结果检查是否完成。
```

**【已核实】** 但该页对它的定位是**“人写提示词”的写作规范**：「好提示词不是一句口号。把目标、输入、动作、约束、输出和验收写清楚，WorkBuddy 才能稳定交付。」[S18]

> **【推断】六段式是“推荐人写结构”，不是「增强提示词」的输出格式。**
> 依据：该页全文是面向人的写作指南与岗位模板，从未声称这是增强器的产出 schema [S18]；且它与 3.1 的四要素（角色/背景/任务/输出格式）并不等价——六段式里没有“角色”，多出“约束/验收”。置信度：高。
>
> **复刻建议**：可以把六段式当作**我们**输出模板的候选之一（它是公开文档里的通用提示词工程写法），但**不要**宣称“WorkBuddy 的增强器输出六段式”。

### 3.3 单候选还是多候选

**【已核实】** 所有可见描述都是“点一次 → 出现**一条**改写结果”，并配套“恢复原文”；没有任何来源提到“换一条 / 多个候选 / 版本对比” [S14][S16][S17]。

> **【推断】单候选（single-shot）为主。** 置信度：中-高。
>
> **易混淆点（务必区分）**：官方确有“任务后续提示词推荐 / 换一条”机制 [S7]——但那是**一轮任务结束后**推荐的“下一步提示词”，填进输入框且不自动发送，与「增强提示词」是两个不同功能 [S7]。不要把“换一条”错记到增强器头上。

### 3.4 规则模板 vs LLM 改写；模型与温度

- **【已核实】** 同客户端内，语音输入的转写结果会「**由模型**对识别出的文字进行调整，并将处理后的内容填入输入框」[S5]——证明该客户端存在“用模型做文本后处理再回填”的既有链路。
- **【未知】** 增强器具体模型、温度、是否走同一模型路由、是否消耗积分，官方无任何说明。
- **【推断】** 增强器是 LLM 改写，而非纯规则模板。
  依据：输出会随输入语义自适应（同一按钮对“写周报/做竞品分析”产出不同结构 [S17]），模板难以覆盖；且客户端已有模型化文本后处理先例 [S5]。置信度：中-高。
- **【推断】** 可能是“规则骨架 + LLM 填充”的混合：先按场景选骨架，再让模型补内容。依据：输出形态高度套路化（编号分节 + 语气 + 字数）[S17]，纯自由生成较少如此整齐。置信度：低（弱推断）。

### 3.5 是否保留原意

**【已核实】** 二手来源明确把它定位为“草稿”而非“定稿”，并强调可继续修改：

> 「提示词增强不是“锁死的”——它会自动生成扩写，但你可以在此基础上手动调整……把它当草稿，不是定稿。」[S17]

> **【推断】设计意图是“扩写/补全”而非“重写/换题意”，但“原意保真”没有任何官方承诺。**
> 依据：措辞一致为“补全/展开/扩写”[S14][S16][S17]，且提供“恢复原文”兜底 [S16]。置信度：中。
>
> **复刻的含义**：把“原意保真”作为**我们必须显式保证、而 WorkBuddy 未承诺**的质量项——这是差异化机会（见附录 R4）。

### 3.6 改写后的输出形态（示例，非官方样本）

作者整理的 20 组“输入 → 增强后”对照，可作为**风格参考**，但**必须标注为第三方整理，不是官方样本** [S17]。典型样例（节选其一）：

> 输入「帮我写周报」→ 增强后：「请根据本周工作记录，按项目分类整理周报。结构：①本周完成事项（含数据支撑）；②进行中事项及进度；③下周计划。语气正式简洁，500 字左右。」[S17]

可归纳的**外部特征**：单段中文指令；用 `①②③` 或分号分节；显式声明**语气**；显式声明**字数上限**；显式声明**受众/平台**适配 [S17]。

## 4. 交互流程

### 4.1 已核实的流程

| 步骤 | 行为 | 来源 |
| --- | --- | --- |
| ① 前置条件 | 输入框为空时**不显示**该入口；输入文字后出现 | [S16] |
| ② 入口形态 | 输入框旁按钮，与「语音输入」并列 | [S14][S15] |
| ③ 触发 | 单击「增强提示词」 | [S16] |
| ④ 结果呈现 | **直接回填/替换到输入框**（“回流”），非弹窗式预览 | [S16][S4] |
| ⑤ 可编辑 | 结果可直接手动修改 | [S16][S17] |
| ⑥ 撤销 | 提供「**恢复原文**」，一键还原成原来的提示词 | [S16] |
| ⑦ 发送 | 仍由用户点发送；增强本身不触发任务执行 | [S17] |

**【已核实】** 关键原文：

> 「老师故意把提示词写的很简单，然后我们单击“增强提示词”，优化之后的提示词如下……如果对优化之后的提示词不满意，可以自己在手动修改，也可以单击“**恢复原文**”，就可以恢复成原来的提示词！」[S16]

### 4.2 来源间的不一致（必须标注）

**【已核实】** 早于按钮形态的描述称它是**开关（toggle）**：

> 「对话框底部有一个**开关**。打开之后，你输入一句话的模糊需求，WorkBuddy 自动帮你展开成一段结构化、精准的指令。」[S17]（2026-06-12）
> 并建议「偶尔**关掉**增强，保持 Prompt 手感」[S17]。

> **【推断】入口形态在 2026-06 → 2026-10 之间发生过变化：开关（常开态）→ 输入框旁按钮（按需点击）。**
> 依据：两篇独立文章描述不同（[S17] 2026-06 “底部的开关” vs [S14]/[S16] 2026-06/2026-10 “输入框旁的按钮”）；且 [S14] 明确是“最近更新后发现新增按钮”。置信度：中。
> **复刻建议**：两种形态都有用户认知基础；推荐**按钮（按需触发）**，因为它不改变默认发送行为，副作用更小。

### 4.3 未知项

- **【未知】** 生成延迟预期、是否有 loading/骨架态、超时多久、能否取消进行中的增强。
- **【未知】** 失败时的降级行为（是否保留原文、是否提示重试）。
- **【未知】** 是否有增强历史/版本记录（“恢复原文”只还原一次，还是支持多步撤销）。
- **【未知】** 快捷键（语音输入有明确快捷键 `⌥`/`ALT` [S5]，但增强提示词未见任何快捷键说明）。

> **【推断】这些“未知”很可能并非文档疏漏，而是该功能确实处于轻量形态**：无快捷键、无历史、无多候选，符合“输入框旁小按钮”的定位 [S14][S16]。置信度：中。
> **对复刻的含义**：DSH 在这些细节上可以**超出** WorkBuddy（见附录 R5/R7），不必被“对齐”束缚。

## 5. 结果输出格式

| 维度 | 结论 | 证据级别 |
| --- | --- | --- |
| 载体 | **纯文本**，回填进输入框 | 【已核实】[S16][S17]；“回流”见 [S4] |
| 结构化程度 | 自然语言指令，内部用 `①②③`/分号分节；**非 JSON、非表单** | 【推断】[S17] 样例形态；无官方 schema |
| 长度 | 明显长于输入（“一句话” → “一段”），无量化数据 | 【推断】[S14][S17] |
| 是否保留原文 | 替换原文本，需靠「恢复原文」还原；**未见“原文+增强”并列** | 【推断】[S16] |
| 元数据 | 无任何标注/来源/版本信息 | 【未知】 |

> **【重要辨析】不要把“提示词模板预览”的行为套到增强器上。**
> 官方“提示词模板”的行为是：悬停显示**灰色预览**，且「输入框已有文字时，预览接在已有内容**末尾**，黑色原文保持不变」「灰字仅供预览，不会进入草稿、撤销记录，也不会被发送」[S6]。
> 这是**模板**的预览语义，与增强器的**替换 + 恢复原文**语义**相反**。两者极易混淆，复刻时需分别设计 [S6][S16]。

## 6. 限制、配额与授权

### 6.1 计费与配额

- **【已核实】** WorkBuddy 采用积分制：「在 WorkBuddy 中，**所有对话相关请求均需消耗积分**」，消耗量取决于模型单价与任务复杂度 [S8]。
- **【未知】** 「增强提示词」是否单独扣积分、扣多少，官方无任何说明。
- **【已核实但不足以采信】** 二手作者称「两个功能都免费，更新到最新版直接用，不需要额外配置」[S14][S15]。这是作者的使用观察，**与官方“所有对话相关请求均需消耗积分”的表述存在张力** [S8]。

## 7. 复刻可借鉴 / 必须适配

### 7.1 可以借鉴（行为与交互模式）

以下属于**通用 UI 交互范式**（业界同类 “improve prompt” 功能普遍采用），不构成对其专有表达的复制：

1. **入口位置**：输入框 composer 旁的单按钮，不打断写作流 [S14]。
2. **按需显隐**：输入为空时隐藏，避免空态误点（也顺带成为“发现性”问题的来源，我们可做得更易发现）[S16]。
3. **一键重写 + 原地回填**：不弹模态框，结果直接进输入框，用户可继续改 [S16]。
4. **一键还原**：「恢复原文」提供零成本回退 [S16]。
5. **单候选、低决策成本**：不做多方案选择器，降低认知负担 [S14][S16][S17]。
6. **改写目标要素**：“角色 / 背景 / 任务 / 输出格式”这类通用提示词工程要素 [S14]；以及公开文档中的“目标·输入·动作·约束·输出·验收”六段式写法 [S18]——这两者都是**公开可得的通用提示词方法**，可作为我们模板的灵感来源。
7. **草稿而非定稿**的产品语气：明确告知用户结果可改 [S17]。

### 7.2 不可复制（红线）

| 不可复制对象 | 依据 |
| --- | --- |
| WorkBuddy 内部的系统提示词、增强器专有指令、专家/Skill 模板文本 | 属商业秘密/著作权 [S11] 12.1；且 9.2(1) 禁止逆向获取 [S11] |
| 其增强输出的**批量抓取**用作训练/评测语料 | 9.2(2) 禁止自动化提取数据 [S11] |
| 整个产品/网页的镜像或“重现或复制本软件及服务” | 9.2(3) [S11] |
| 名称 “WorkBuddy”、Logo、图标、UI 截图、产品文案 | 商标与著作权 [S11] 12.1、9.2(4) |
| 通过补丁改写其运行指令以改变输出（“破甲”） | 9.2(8) 明令禁止 [S11] |

> **【推断】合规的安全做法**：只依据**公开可观察的行为描述**（如本笔记引用的公开文章与官方文档）提炼需求；提示词文本、模板、评测集**全部自研**；不逆向、不批量抓取其输出。置信度：高。

## 附录：DSH 复刻需求推导

以下每条都可回溯到上文对应小节；`R#` 供后续设计文档引用。

- **R1（溯源 §1.2、§4.1）入口必须是“输入框旁、有文本才出现”的轻量按钮。**
  理由：WorkBuddy 的入口形态已是用户认知基线；按需显隐可避免空态误触。**但**要把“找不到功能”这个已知痛点修掉（S16 的整篇文章正是在解答“找不到”）：首次使用时给一次可关闭的提示，或在空态禁用而非隐藏。

- **R2（溯源 §2.1、§2.2）增强结果必须严格绑定“当前会话 / 当前草稿”，禁止跨会话共享。**
  理由：官方自己踩过「跨会话泄漏」的坑 [S4] 5.1.0。这是硬性正确性要求，不是体验优化。

- **R3（溯源 §4.1、§5）采用“原地回填 + 可编辑 + 一键恢复原文”，不要弹模态预览。**
  理由：WorkBuddy 的实际语义是**替换**而非预览 [S16]；同时必须与官方“模板灰色预览（不覆盖原文、不入撤销栈）”的语义**明确区分** [S6]，两者不可混为一谈。

- **R4（溯源 §3.5）把“原意保真”做成显式契约，这是相对 WorkBuddy 的差异化优势。**
  理由：WorkBuddy 只以“草稿、可改”暗示非破坏性 [S17]，**并无原意保真的官方承诺**（未知项）。DSH 可提供“保真校验/差异高亮/仅补全不改写”开关。

- **R5（溯源 §4.3）补齐 WorkBuddy 未见的工程细节：取消、超时降级、失败保留原文、进度反馈。**
  理由：这些在公开资料中全部为【未知】。最低要求：增强失败时**原文一字不动**，并给出可重试提示。

- **R6（溯源 §3.1、§3.3、§3.6）输出默认“单候选、中文分节指令”，显式包含角色/背景/任务/输出格式四要素，并按需附语气与字数约束；多候选只作为可选增强项，并明确标注这是超出 WorkBuddy 的设计。**
  理由：四要素为多源一致的可观察效果 [S14][S16]；语气/字数/平台是样例中的稳定外部特征 [S17]；无证据表明 WorkBuddy 提供多候选（§3.3），而多候选会显著抬高成本与延迟，需产品决策。**不要**照搬“六段式”并宣称是官方格式（§3.2）。

- **R7（溯源 §6.2、§6.3、§7.2）合规红线写进开发约束：提示词与模板 100% 自研；不逆向、不抓取其输出、不使用其商标与素材。**
  理由：协议 9.2(1)(2)(3)(4)(8) 明文禁止 [S11]；产品名与 Logo 属其商标 [S11] 12.1。此项应作为发布前检查清单的一项。

- **R8（溯源 §6.1）计费口径需自行定义并明示，不要照搬“免费”说法。**
  理由：二手作者称“免费”[S14]，但官方称所有对话相关请求均消耗积分 [S8]，二者冲突且无官方针对该功能的说明（§6.1 存疑项）。DSH 应自行决定是否计费并透明告知。
